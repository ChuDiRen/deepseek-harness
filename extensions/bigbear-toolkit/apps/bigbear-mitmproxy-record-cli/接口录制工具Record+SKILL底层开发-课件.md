# 接口（API）录制工具Record +SKILL底层开发

## 一、为什么要开发这个工具：痛点与核心价值
### 1. 业务背景和传统方案的痛点
当下我们经常项目没有接口文档，或者需要把 App / 桌面应用发出的接口请求交给 AI（豆包、DeepSeek 等）完成接口文档生成、测试用例生成、接口分析等工作。

Web 端我们做了页面录制工具（截图 + DOM），设备端做了画面录制工具（截图 + UI 层级），但**纯接口数据**是另一类重要素材——请求方法、地址、参数、响应体，这些是生成接口文档和接口测试用例的直接依据。

以往的同学都会有如下的想法和考虑：

#### 方案1：手动抓包 + 复制整理
+ 效率极低：用抓包工具一条条复制，重复机械劳动
+ 容易出错：请求和响应对应关系容易混乱
+ 无法批量：几十个接口手动整理几乎不现实

#### 方案2：让 AI 直接去调接口
很多人会疑问：能不能让 AI 自己发请求、抓返回？
**答案是不推荐，核心有几个不可回避的问题**：

1. **要抓的是"真实客户端发出的流量"**：App、桌面应用发出的请求带着登录态、签名、加密参数，AI 凭空构造不出来
2. **交互态无法捕捉**：很多接口是点击按钮、滑动、输入后才触发的，AI 无法代替人操作
3. **多端覆盖不了**：手机 App、桌面软件、小程序，AI 都无法直接附着
4. **安全边界**：把业务系统直接交给外部 AI 去调，存在数据外泄与不可控风险

**AI 要准确理解接口，必须拿到真实完整的流量数据：**

+ **请求信息**：方法、URL、请求头、请求体
+ **响应信息**：状态码、响应头、响应体

### 2. 解决方案：自研接口录制工具
用 mitmproxy 做中间人代理，把客户端发出的 HTTP/HTTPS 流量"照单全收"，标准化落盘后直接喂给 AI 做后续分析。

+ 真实流量：抓到的就是客户端真实发出的请求
+ 保留状态：登录态、签名、加密参数全部天然携带
+ 多端通用：Web / 手机 H5 / App / 桌面应用，一套方案全搞定
+ 结构化输出：统一格式，AI 可直接解析

## 二、技术选型：mitmproxy vs Fiddler vs Charles
:::tips
那么现在最重要的就是技术的选型。
:::

### 1. 选型核心考量
我们的工具要做成"可被 AI / 工具链调用的底层底座"，不止要抓包，还要满足：

+ 可编程扩展：自定义过滤、落盘逻辑
+ 自动化支持：纯命令行启动、参数控制，易嵌入流水线
+ 多端流量支持：Web / APP / 小程序 / 桌面应用一套通用
+ 跨平台兼容

### 2. 三大主流方案对比
| **对比维度** | **mitmproxy** | **Fiddler** | **Charles** |
| --- | --- | --- | --- |
| **可编程扩展** | 原生支持 Python 插件开发，可自定义过滤、落盘逻辑，深度定制能力强 | 扩展能力有限，偏向桌面 GUI 工具，深度定制难度大 | 扩展能力弱，以人工操作为主 |
| **自动化支持** | 纯命令行运行，可通过参数完全控制启动、过滤、输出，易嵌入流水线 | 偏向 GUI 操作，自动化调用能力弱 | 桌面 GUI 工具，自动化适配差 |
| **跨平台兼容** | 全平台原生兼容，适配 Windows/macOS/Linux | 偏向 Windows 生态，跨平台能力弱 | 跨平台支持较好，但可编程性不足 |
| **多端流量支持** | 可抓取 Web、APP、小程序、桌面应用等任意端流量，一套方案通用 | 以 Web/Windows 客户端为主 | 全端支持，但无法深度定制 |
| **工具链嵌入** | 可无缝嵌入自研工具链，作为底层驱动被上层调用 | 难以嵌入自研体系，适合人工调试 | 难以嵌入自研体系，适合人工调试 |

### 3. 结论：选择 mitmproxy
接口录制需要**深度定制、自动化调用、多端统一适配**，mitmproxy 是唯一能无缝融入工具链的方案，桌面抓包工具仅适合人工调试场景，不适合作为统一底座。

### 4. 代理端录制工具定位
> **基于 mitmproxy，支持命令行与 Web 两种运行方式，可同时抓取多个端的接口流量，适用范围最广。**

+ **命令行方式**：AI / 脚本可驱动，纯参数控制
+ **Web 方式**：mitmweb 网页实时看流量 + 控制面板一键停止
+ **多端通用**：桌面应用（Electron / Qt / .NET / Java Swing）、手机 H5 / APP、任意 HTTP 客户端

## 三、工具形态设计：命令行 CLI 工具 + Web 控制台
:::tips
**问题：**那么到底我应该做成什么样子的呢？
:::

我们的核心调用方是 AI（SKILL 底层调用），因此工具需要满足：

+ **AI 易调用**：大模型可直接拼接命令参数，无需图形界面交互
+ **可脚本化**：可编写批量脚本
+ **跨平台**：Windows / macOS / Linux 无缝运行
+ **轻量高效**：无 GUI 开销，启动速度快
+ **易集成**：可轻松嵌入 SKILL、流水线、其他业务系统

所以我们可以通过命令行的方式去进行调用更加稳妥；同时因为抓包过程需要"看得见、控制得住"，还要配套一个 Web 控制台。

例如：

```bash
xxx record                      # 启动录制（默认打开控制面板 + 浏览器）
xxx record --no-browser         # 桌面应用 / APP 场景，不打开引导浏览器
xxx install-ca                  # 仅安装 HTTPS 解密证书
xxx check                       # 环境检查
xxx stop                        # 停止后台录制
xxx --help                      # 显示对应的帮助信息
```

启动后：
+ 客户端把代理指向 `127.0.0.1:8080`，所有 HTTP/HTTPS 请求被录制
+ 浏览器打开控制面板（`http://127.0.0.1:9090/`），实时看流量 + 右下角"🛑 停止录制"按钮
+ 输出目录自动生成对应批次的 `raw{NN}.json`

### 版本1：最简原型版 —— 跑通核心链路
**目标**：先做出能用的最小版本，验证「启动 mitmproxy 代理 → 客户端走代理 → 流量落盘成 raw JSON」的核心可行性。

**做成什么样：**

+ 形态：极简命令行工具
+ 调用方式：终端输入一条命令即可启动代理
+ 核心动作：环境检查 → 启动 mitmproxy（默认 8080）→ 客户端指向代理 → 插件把每个请求转结构化数据落盘

**所需环境：**

1. Python 3.9+ 环境（授课使用 3.11 版本）
2. mitmproxy（缺了工具自动装）

**输出形式：**

+ 在输出目录（默认 `AI-信息采集`）下按批次生成 `raw{NN}.json`
+ JSON 包含每条请求的「请求 + 响应」两大块
+ 核心目的：先把整个技术流程跑通，证明方案可行

**本环节AI生成提示词**

> 我要做一个接口（API）抓取录制工具，你帮我一步步实现。先讲背景：
>
> 我们已经做了 Web 端（页面录制）和设备端（手机画面录制）工具，现在要做接口端：通过抓取客户端发出去的 HTTP/HTTPS 请求，把"请求方法、地址、请求头、请求体、响应状态、响应体"录下来，存成文件，供后面直接丢给大模型生成接口文档、测试用例。
>
> 技术方案我定了：用 mitmproxy。它是中间人代理——客户端把流量指向它，它再转发给真实服务器；我们写一个插件（addon）订阅每个请求，把它转成结构化数据落盘。用 Python 写，做成本地命令工具。
>
> 存盘格式有硬要求，必须跟已有的接口工具完全一致（下游程序直接读）：一次运行 = 一个批次，用时间戳当文件夹名；每条请求存成"请求(request)"和"响应(response)"两大块，请求块含：id、方法(method)、地址(url)、请求头(headers)、请求体(body)、时间戳(timestamp)；响应块含：状态码(status)、响应头(headers)、响应体(body)、时间戳。输出文件按 raw01.json、raw02.json 这样编号。二进制内容（图片、视频等）别硬存文本，加个 base64 前缀存编码。
>
> 开发方式：分阶段来，我一个阶段一个阶段告诉你做什么。每次做完，简单说一下做了啥、怎么验证、有没有遗留问题，我确认了再继续。工程结构、文件名你自己拿主意。
>
> 第一阶段，先做个最简陋但能跑通的最小版本：
>
> 目标就一个——我敲一条命令，它能起一个 mitmproxy 代理（默认监听 8080 端口），然后我把某个客户端的代理指到 127.0.0.1:8080，这个客户端发出的 HTTP 请求就会被录下来，存成 raw01.json 这样的文件，放在"AI-信息采集/时间戳批次号"目录下。
>
> 具体要求：命令入口做成装好后能全局直接敲的，大概长这样：xxx record。启动前检查环境：没装 mitmproxy 就提示/自动 pip install。写一个 mitmproxy 插件，订阅"请求完成"事件（请求+响应都齐了）时，把这条记录转成我开头说的那个格式，落盘。一个文件里装多条记录（数组），够一批就写盘；停止时把没写完的也补上。运行时多打点日志，告诉我监听在哪个端口、存到哪了。
>
> 先不要做 HTTPS 解密、不要做网页控制台、不要做过滤规则，那些后面再说。做完告诉我怎么验证（比如用 curl -x 127.0.0.1:8080 发个请求看有没有落盘）。

**本阶段验收**：

```plain
# 启动录制
xxx record

# 另开终端发一个测试请求
curl -x http://127.0.0.1:8080 https://httpbin.org/get

# 检查落盘
AI-信息采集/
└── 20260829-143000/
    └── raw01.json     # 含该请求的 request + response
```

### 版本2：HTTPS 解密版 —— CA 证书自动安装
**但是目前还是有需要进行优化：**

1. 只能抓 HTTP 明文，App 和网页大部分是 HTTPS，抓到的全是加密乱码，必须解密。

**做成什么样：**

+ 新增能力：mitmproxy 生成自己的 CA 证书，首次运行自动装到系统证书库
+ 核心逻辑：客户端信任证书后，HTTPS 流量被透明解密成明文再落盘

**本环节AI生成提示词**

> 第二阶段，加 HTTPS 解密能力。现在只能抓 HTTP 明文，很多 App 和网页都是 HTTPS，不处理的话抓到的全是加密的乱码。
>
> 具体要求：
> - 让 mitmproxy 生成自己的 CA 证书；首次运行自动把证书装到系统证书库（Windows 用 certutil、macOS 用 security、Linux 用 update-ca-certificates；装失败就给出手动安装命令提示，别让程序崩）
> - 加一个子命令：只安装证书不启动录制（比如 xxx install-ca）
> - 加一个环境检查子命令（比如 xxx check），打印 Python 版本、mitmproxy 有没有装、证书生成没生成
> - 客户端信任证书后，HTTPS 请求要能被解密成明文录下来
>
> 做完了告诉我怎么验证（比如 curl -x 抓一个 https 地址看 body 是不是明文）。

**本阶段验收**：`xxx check` 环境检查全绿；`xxx install-ca` 证书装好；`curl -x` 抓 https 地址 body 是明文。

### 版本3：控制面板版 —— Web 实时看流量 + 一键停止
**但是目前还是有需要进行优化：**

1. 纯命令行看不到抓包过程，也不方便优雅停止，需要"边看边抓、点一下停止"。

**做成什么样：**

+ 新增能力：mitmweb 网页实时看流量 + 控制面板注入"🛑 停止录制"浮动按钮
+ 核心逻辑：mitmweb 是单页应用，关标签页不会停后台进程，所以用一个"包装层"把停止按钮注入页面，点按钮触发优雅停止（补落盘 → 停代理 → 结束程序）

**本环节AI生成提示词**

> 第三阶段，加一个网页控制台，让我能在浏览器里实时看到抓到的流量，并且能优雅地停止录制。
>
> 先跟你说清楚一个坑：mitmweb（mitmproxy 自带的网页界面）是单页应用，直接关掉浏览器标签页不会停掉后台进程，所以"关页面 = 停止"这条路走不通。我们换一种做法：
>
> 具体要求：
> - 启动 mitmweb 网页界面（默认 8081），打开浏览器能实时看到流量列表
> - 再起一个"控制面板"包装服务（默认 9090），它把请求转发给 mitmweb 页面，同时往页面里注入一个浮动"停止录制"按钮
> - 我点那个按钮，后台就优雅停止：把没写完的请求落盘、停掉 mitmweb、结束程序
> - 启动时等 Web 界面端口就绪再打开浏览器；给我打印清晰的提示：代理端口、网页地址、怎么配置代理、怎么停止
> - 提供几个参数：--no-browser（不自动开浏览器，给 App/桌面应用场景用）、--port / --web-port / --control-port（自定义端口）
>
> 做完了给我一份怎么验证的操作步骤（启动、看流量、点停止、检查落盘）。

**本阶段验收**：启动后浏览器打开控制面板 → 客户端走代理发请求 → 网页实时看到流量 → 点"🛑 停止录制" → 程序优雅退出、raw 文件完整落盘。

### 版本4：标准生产版 —— 过滤规则 + 检测脚本
**但是目前还是有需要进行优化：**

1. 抓了一堆 css / js / 图片等静态资源，噪音太多；录出来的 raw 文件可能很大，直接打开会刷屏。

**做成什么样：**

+ 新增能力：URL 过滤规则 + 资源过滤预设 + 按域名分文件
+ 新增能力：检测脚本，只输出接口摘要（接口数、方法、状态码），不读完整 body

**本环节AI生成提示词**

> 第四阶段，加过滤规则和检测脚本，让录出来的数据更干净、更好用。
>
> 1. 过滤：加这几个参数——
>    - 排除规则：--exclude，给 URL 正则，命中就丢掉（可多次）
>    - 白名单：--include，给了就必须命中才保留
>    - 资源过滤预设：--resource-filter，三种：off（全收）、static（跳过 css/js/图片/字体/视频等静态资源）、api-only（在 static 基础上只留 json/xml/form/text 这类接口响应，把 HTML 页面也过滤掉）
>    - 按域名自动分文件：--auto-split-by-domain，每个域名一个 raw 文件
> 2. 检测脚本：写一个独立脚本（比如 inspect_recording.py），用来"看"录制结果——注意 raw 文件可能很大（几百 KB 到几 MB），所以脚本只输出摘要：每个文件的接口数、每个接口的 [方法] [状态码] URL、按方法/状态的汇总。不要输出完整 body。
>
> 做完了给我一份怎么验证的清单。

**本阶段验收**：`--resource-filter api-only` 只录到业务接口；`inspect_recording.py` 快速给出接口清单和数量。

## 六、SKILL 层封装开发
SKILL 是工具的上层交互封装，负责屏蔽底层技术细节，让用户通过自然语言就能完成录制，同时承接 AI 的调度。

### 第一步：梳理 SKILL 完整执行流程
1. **环境检查**
   - 校验 Python 版本是否符合要求
   - 检查 mitmproxy 是否安装（未装则自动 pip install）
   - 检查 CA 证书是否生成/安装
2. **参数确认**
   - 确认要录哪个端：浏览器 / 手机 H5 / APP / 桌面应用（决定是否 --no-browser）
   - 确认输出目录（除非用户明确指定，否则用默认）
3. **调用录制**
   - 拼接命令行参数，调用底层 CLI 工具
   - 实时反馈执行进度（正在启动代理、正在打开控制面板...）
4. **配置代理**
   - 浏览器：系统代理 / 扩展
   - 手机 H5：Wi-Fi 设置手动代理，IP 填电脑内网 IP，端口 8080
   - 桌面应用：应用网络设置 → 代理 127.0.0.1:8080
5. **结果检测与返回**
   - 录制完成后调用检测脚本拿摘要（**不要用 Read 直接打开 raw 文件，可能几百 KB ~ 几 MB**）
   - 返回：文件路径、接口总数、按方法的分布
   - 询问用户下一步：继续追加录制 / 生成接口文档 / 生成测试用例

SKILL 交互示例

```plain
用户：帮我录制一下购物车 App 的接口
SKILL：请先确保手机和电脑在同一 WiFi，手机 Wi-Fi 设置手动代理为
       <电脑IP>:8080，并已信任证书。正在启动录制...
SKILL：录制完成！批次号 20260829-143000，共抓到 8 个接口
       （POST 5 / GET 3）。需要我帮你生成接口文档吗？
```

### 第二步：生成对应的 SKILLS
1. 遵循技能规范：生成技能时，务必遵守标准规范，以确保其他工具都能直接调用使用。详细规范请参考：Skill 规范（skill-creator / 平台技能规范）

2. 在当前项目路径下创建一个技能目录（如 `.claude/skills` 或对应平台的技能目录）

3. 把如上梳理的流程告诉 AI，让它按规范生成 SKILL 描述（触发场景、输入参数、执行步骤、输出产物）

**本环节AI生成提示词**

> 工具做完了，帮我把这个工具变成一个 AI 可以自动调用的技能（SKILL）：
>
> 写清楚：什么时候该用它、要什么输入、会输出什么。调用流程大概这样：
> 1) 先检查环境（Python、mitmproxy 缺啥装啥，装不了提示用户）
> 2) 再确认要录哪个端（浏览器 / 手机 H5 / 桌面应用），把对应的代理配置方法告诉用户
> 3) 然后启动录制（给出启动命令，手机 H5 用 --no-browser）
> 4) 录制结束，用检测脚本拿摘要（文件路径、接口数、方法分布），不要直接打开 raw 文件看内容（会很大）
> 5) 问用户下一步：继续追加 / 生成接口文档 / 生成测试用例
>
> 别贴大段源码，写成"调用说明"就行。过程中要用户做决定的时候，停下来问。

### 第三步：测试与验证
接下来，我们就可以进行测试：

+ 真机测试：启动录制，配置代理，操作客户端产生流量，验证目录、raw 文件是否正确生成
+ 用检测脚本拿接口摘要，验证数量、方法、状态码正确
+ 用自然语言触发 SKILL，验证是否能正确提取参数、调用工具、返回结果
+ 模拟未安装环境的场景，验证安装引导是否准确可用

**重新打开一个 Agent 对话框**，查看是否能正确的驱动起来。

### 真机手工验收清单
1. 执行 `xxx check` 环境检查通过
2. 执行 `xxx record` 启动，浏览器自动打开控制面板

8. 把 raw 文件交给下游大模型，验证可直接消费（生成接口文档/测试用例）

### 常见问题与排查
| 现象 | 排查 |
| --- | --- |
| 录完 raw 文件为空（最常见） | ① 检查客户端代理是否真的指向 8080（`curl -x` 验证）；② 是否开了 api-only 过滤把请求都丢了；③ 手机代理 IP/端口是否配对、APP 是否 SSL Pinning |
| 抓到 HTTPS 全是乱码 | 证书没装好，执行 `xxx install-ca`；手机需访问 `http://mitm.it` 下载证书并信任 |
| 抓不到手机流量 | 手机和电脑必须同一局域网，代理 IP 填电脑内网 IP（`ipconfig` 查看），端口 8080 |
| 停止后文件没写全 | 用控制面板"🛑 停止录制"按钮或 Ctrl+C 优雅停止，不要强杀进程 |
| 端口被占 | 用 `--port` / `--web-port` / `--control-port` 换一个 |
